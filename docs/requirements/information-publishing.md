# 信息发布与网站服务产品需求

## 1. 文档责任

本文是 `jilinjobs-cms` 当前信息发布与网站服务的长期产品需求 owner，回答“产品为什么存在、面向谁、提供什么稳定能力、哪些可观察行为和长期约束必须成立”。

本文不维护数据库 migration 编号、源码目录、前端组件、具体框架装配、Site Package 物理路径、Historical Migration 实现步骤、Execution Unit、PR / Actions 或其他高频实现状态。CMS 业务对象、身份、状态、生命周期与跨对象不变量由 `docs/requirements/cms-domain.md` 统一定义；跨 Feature 的长期系统边界由 Architecture Authority 定义。

历史 V4.x 文档、局部 Requirement Change 与已完成工程 Requirement 继续作为来源和追溯材料，只有被本文、Domain Authority 或后续 Architecture / Specification 明确吸收的语义才构成当前长期事实。

## 2. 产品目标

吉林省高等学校毕业生就业信息网需要同时满足：

1. 面向社会公众提供中心主站的信息发布、政策与服务内容；
2. 在主站信息架构下提供“中心党建”专题入口及其独立红色视觉表达；
3. 为运营人员提供可持续维护内容、结构、展示和站点属性的 CMS 管理能力；
4. 在不复制旧站前端实现的前提下，保持原站主要信息架构、视觉识别和公共访问习惯，并完成必要的现代化适配；
5. 让稳定工程设计与持续运营数据各有清晰责任，不为了“可配置”而把所有页面结构、视觉和固定集成都变成后台配置；
6. 让正式内容、稳定站点定义、历史数据与公开呈现可以独立演进，不把某个具体前端实现变成产品数据事实来源。

## 3. 用户与利益相关者

### 3.1 公开访问者

公开访问者可以浏览主站与中心党建公开内容，通过稳定 URL 访问栏目、文章、单页和专题入口，并按当前内容对象的语义进入站内详情或外部权威来源。

### 3.2 CMS 运营人员

运营人员使用管理端维护当前已接受的 CMS 内容、内容结构、运营展示、网站属性和静态资源。当前阶段不依赖完整用户、角色和权限体系；未来认证授权属于独立需求，不能由当前 UI 中的临时身份假设提前实现。

### 3.3 项目维护者

项目维护者负责稳定页面设计、工程集成、版本化站点基线、历史数据迁移和运行环境。维护者不能通过实现便利反向改变运营人员和公开访问者已经接受的产品语义。

## 4. 产品范围

### 4.1 当前范围

当前信息发布与网站服务至少包含：

- 中心主站公开前台；
- 主站“中心党建”专题入口、栏目列表、文章详情与独立红色视觉主题；
- CMS 管理端；
- 栏目与文章；
- 单页与单页分组；
- 导航位置与导航条目；
- 通用列表与列表项；
- 宣传展示位与展示内容；
- 网站属性；
- 静态资源；
- 稳定公开 URL、站内跳转与外链行为；
- 富文本内容编辑与安全呈现；
- 站点初始化所需的稳定结构和必要初始运营数据；
- 历史内容在有明确 Authority 时的离线迁移与可追溯导入；
- 响应式、基础浏览器兼容、可访问性与基础搜索引擎友好所需的公开体验。

### 4.2 当前不在范围

当前阶段不自动建设：

- 完整用户、账号、角色、统一认证与权限体系；
- 多级内容审核；
- 评论、点赞、收藏、投稿、留言、工单；
- 通用全文搜索；
- 通用可视化 Page Builder；
- 任意多租户 / 任意多站点 CMS 平台；
- MQ、Redis、MinIO 等无当前真实需求的基础设施扩张；
- 生产发布拓扑、正式发布流程或部署平台重构；
- 没有当前证据支撑的党建专属 CMS 数据模型或独立后台；
- 因未来可能替换前端而预先建设无证据的通用插件框架或 Repository 拆分。

## 5. 产品信息架构与运营能力

### 5.1 内容管理

CMS 必须能够维护文章、单页和通用列表等主要内容。栏目、单页分组、导航位置和列表定义承担稳定组织上下文；运营人员在明确上下文中维护成员数据，不应被迫理解数据库、Migration、Frontend module 或其他实现术语。

### 5.2 内容结构

栏目和导航承担站点内容结构。稳定公开身份必须支持直接访问、面包屑和长期链接恢复，但产品界面使用“栏目、单页、单页分组、列表、位置标识、属性标识”等运营人员可理解的术语，不要求其理解内部类名或表名。

### 5.3 运营展示

宣传展示与通用列表用于稳定页面区域中的运营内容投放。展示数据与页面视觉职责必须分离：CMS 维护“有什么内容、顺序、有效性、目标和必要图片”，具体页面如何排版、使用何种尺寸或视觉组合由公开页面设计决定。

### 5.4 站点设置与资源

网站属性用于少量需要运营维护的站点级信息和低风险行为参数。静态资源管理用于受控上传、选择、替换和清理站点资源。基础设施地址、安全限制、数据库连接和 CI / 部署参数不作为 CMS 运营属性。

## 6. 主站公开体验

主站继续以吉林省高等学校毕业生就业信息网的既有信息架构和主要视觉识别为业务参照，稳定提供：

- 首页；
- 栏目列表；
- 站内文章详情；
- 独立单页；
- 单页分组成员页；
- 固定第三方业务集成入口；
- 主导航、快捷入口、轮播、资讯区、业务指南、宣传区域、网站链接和 Footer 等已确认页面能力。

公开站只消费当前正式业务数据和公开 contract，不复制第二份运营数据。无需运营维护的固定页面结构、装饰和第三方 seam 可以继续作为工程设计；一旦真实需求要求运营维护，再通过 Requirement Change 判断是否进入 CMS。

## 7. 中心党建产品定位

“中心党建”是中心主站信息架构下具有独立视觉主题的专题入口，不是第二个独立业务网站。

当前长期要求：

- 主导航可以进入 `/party/`；
- `/party/**` 保持独立红色主题和内容模板；
- 高层声音、工作动态、党规党章、理论学习、主题教育属于已确认的党建内容范围；
- “学习园地”是党规党章与理论学习的页面分组，不新增独立内容类型；
- 主题教育是可访问内容栏目，但不因此成为入口页第五个固定内容区；
- 党建内容继续复用通用栏目、文章和列表能力；没有真实专属工作流或数据模型证据时，不新增党建专属 CMS 类型；
- 主站与中心党建对公共 Navigation / Footer 的业务信息保持一致，同时允许各自拥有不同主题和页面设计。

## 8. 公开 URL 与跳转行为

当前 canonical URL 至少保持：

```text
Main
/                             首页
/column/{alias}               栏目
/article/{id}                 站内文章
/page/{alias}                 独立单页
/page/{groupAlias}/{alias}    单页分组成员

Party
/party/                       中心党建入口
/party/column/{alias}         党建栏目
/party/article/{id}           党建站内文章
```

公开 URL 是产品 contract，不由具体 HTML entry、Vue component、Router file 或其他实现结构决定。

外链内容直接进入真实目标；不同业务对象继续按各自 Domain contract 拥有外链身份和打开行为，不建立无业务意义的统一 Link 对象。

## 9. 内容生命周期与公开可见性

文章、列表项、展示内容、导航、网站属性等只有在各自满足启用、发布、有效期和数据完整性规则时才进入公开投影。

文章至少保持草稿、已发布、已撤回生命周期；编辑不会自动等于发布。只有已发布内容进入正常公开发现范围，撤回后退出公开列表和投放，重新发布后可以按既有有效关系恢复。

创建时决定来源身份的对象不得通过普通编辑静默切换成另一种业务身份；需要改变来源语义时应形成显式新对象或新的受控变更流程。

## 10. 富文本与结构化内容

运营人员需要成熟、稳定、中文友好的 Rich Text authoring。对 Rich Text 内容，HTML 是唯一正文 Authority，不引入第二套 editor-internal 状态与之并行持久化。

当页面的 card、section、step 等结构本身属于产品语义时，不应长期把它压平成任意 HTML。Page 必须具有明确的 primary content authority，并通过显式内容模型和 renderer 呈现；未知或不支持的内容模型不能静默回退为 Rich HTML。

本需求不因此建设通用 Page Builder，也不要求所有单页都结构化。

## 11. 历史内容与来源依赖

历史内容迁移是受控、可追溯的离线能力，不是公开站运行时依赖。

长期要求：

- 已接受的历史内容必须具有稳定来源身份和 provenance；
- 稳定导入不依赖 Legacy Source 在线可用性；
- 未解决、缺失、冲突或待客户确认的数据不得为了“全绿”而静默猜测、删除或覆盖；
- 站点稳定结构、普通初始运营数据与历史迁移内容必须保持不同生命周期；
- 完成初始化或导入后的普通 Runtime 内容继续遵守运营生命周期，不因 Repository baseline 自动反复覆盖。

## 12. 资源与安全约束

CMS 资源必须执行安全路径、允许类型和真实媒体内容校验。公开站不得执行运营人员上传的任意 HTML/JavaScript 资产。

正在被稳定站点基线或当前 CMS 数据直接引用的资源必须受到删除保护；系统无法证明所有富文本、CSS 或外部引用时，普通资源删除仍需向运营人员表达残余风险。

外链以新窗口打开时必须使用等价于 `noopener noreferrer` 的安全约束。当前没有产品需求要求所有外链统一增加离站确认或外链徽标。

## 13. 质量与体验约束

长期产品至少要求：

- Main / Party 稳定 URL 可直接访问与刷新；
- 页面在桌面和移动端保持可用，不复制旧站固定宽度导致的明显横向溢出；
- 内容加载、错误、空态和不支持状态必须可诊断，不通过静默 fallback 掩盖失败；
- 图片、链接、表格等正式内容在 Admin 保存和 Public 展示之间保持用户可感知语义；
- 公开端和管理端不得因当前实现替换而改变既有业务对象身份、内容 ownership 或 canonical URL；
- 有视觉验收要求时，自动行为验证不能替代必要的视觉 / Human Review。

## 14. 项目级验收不变量

未来 Feature / change 若触达本产品范围，至少不得破坏以下不变量：

1. 运营数据只有一个长期业务 Authority，不在 CMS、Frontend 常量和迁移数据间并行双写；
2. Main / Party 的业务定位、内容作用域和 canonical URL 不因工程重构漂移；
3. CMS 业务对象的稳定身份、来源身份、发布生命周期和 operator ownership 不被实现捷径绕过；
4. 稳定站点定义、普通 Runtime 数据和 Historical Migration provenance 不被混成同一生命周期；
5. 公开呈现实现可以替换，但不能反向拥有正式 CMS 内容或历史迁移事实；
6. Product Requirement 不因数据库、框架、目录或 migration 编号变化而失效；
7. 任何真实产品歧义必须回到 Requirement Clarification / Human Authority，而不是在实现中静默选择。

## 15. 非决策

本文不决定：

- 具体前端框架、SPA / SSR / SSG / Hybrid；
- Backend module 数量和源码目录；
- 当前 Flyway 文件编号；
- Site Package、Migration 或 Runtime 的具体物理目录；
- Rich Text editor 品牌或版本；
- Review Environment / CI 拓扑；
- 当前 Ready Execution Unit、Planning Candidate 排序、PR 或发布状态。

这些由对应 Architecture、Specification、Technical、Work 或 GitHub Current Evidence owner 决定。
